Scripture Map

A Strapi plugin where agents read every sermon, article, blog and Q&A, suggest the Bible passages each one teaches, and editors decide. The approved links power one API: /Genesis/1/1, /Genesis/1 or /Genesis.

How strongly related

Every link has one of three strengths

Agents and editors don't score resources from 0 to 100. They pick one of three strengths. That's easier to agree on, easier to review, and it decides what the website shows.

●●●

Primary

The resource teaches this passage. A sermon on Genesis 1:1–3 is primary for those verses.

Shown on the site, first
●●○

Substantial

A real section of the resource treats the passage, but it isn't the main text.

Shown on the site, after primary
●○○

Mention

Quoted or cited in passing. Kept for search and for editors.

Never shown on the site
Workflow

Agents suggest, editors decide

Each resource moves through five steps. Agents do the reading at scale. Only an editor can approve a link, and agents never overwrite an editor's decision.

1

Import

Read the existing Scripture field. Specific references like “Genesis 1:1–5” become suggestions. “Selected Scriptures” or a blank field sends the resource to step 2.

Script
2

Read

An agent reads the transcript or article and suggests passages with a strength, a quote as evidence, and how much of the resource dwells on each.

Agent
3

Check

Code confirms every quote appears in the source text. A second model weighs in on low-confidence suggestions. Failed checks are dropped.

Code + second agent
4

Decide

An editor approves, changes the strength or range, or rejects with a reason. Editors also pin the top 3 for busy passages.

Editor
5

Publish

Approved links go live in the API right away. The site shows 3 per passage, with More when there are more.

API
Not analyzed→Suggestions waiting→ReviewedorNo main passage
  • Agents never approve.They write suggestions only. An editor approval is the only way a link reaches the site, at least until the agents' accuracy is proven.
  • Editors always win.Re-running an agent never changes a link an editor approved, rejected, re-ranked or edited.
  • Evidence or nothing.Every suggestion carries a quote and a timestamp or paragraph. A quote that isn't in the source text is dropped automatically.
  • Topical is a real answer.“No main passage” closes a resource, so it doesn't keep coming back to the queue.
Screens

Two ways in: by content or by Scripture

Editors mostly work through content: a sermon series, this month's articles, every blog with a blank Scripture field. So Resources is the main screen. It's a filtered list of resources, each showing its passages and strengths. Bible is the second way in, for checking what a passage shows on the site. The same links also appear inside the Content Manager. On a phone, scroll each screen sideways.

Under the hood

One table of links, ranked by fit

Links live in one new collection, scripture-link, separate from the resources. That keeps imported fields like Scripture untouched, so content sync and editor edits don't collide.

FieldHolds
resourceType, resourceIdWhich sermon, article, blog, Q&A, devotional, series or study guide
startVerse, endVerseThe passage as two verse numbers, for example 01001001 to 01001003
strengthprimary, substantial or mention
statussuggested, approved or rejected, plus a reason when rejected
sourceScripture field, agent, editor, or inherited from a series
evidenceQuote, timestamp or paragraph, share of the resource, and which model suggested it
pinnedRankAn editor's manual order for the top 3
reviewedBy, reviewedAtWho decided, and when

Within each strength, a link that matches the requested passage closely ranks above one that covers much more. A sermon on all of Genesis 1 is a strong match for /Genesis/1 and a weak one for /Genesis/1/1. Editor pins always come first.

fit = strengthWeight × overlap(request, link) ÷ span(request ∪ link)
Plan

Build it in five phases, plus an option

Each phase ships something editors can use. The first phase already gives the site real results, from the Scripture fields that name a specific passage.

  1. P1
    Links table and importVerse numbering, a reference parser, the scripture-link collection, an import from specific Scripture fields, and the read API.
  2. P2
    Resources screen and Content Manager panelFilter and work through content, approve imported links, and see passages while editing. Then the Bible tab for pinning the top 3.
  3. P3
    Agents and ReviewAgents read sermon transcripts first. Quote checks, the Review screen, and reasons on every rejection.
  4. P4
    Accuracy setEditors label about 100 passages by hand. Every agent change is scored on how many of its top 3 picks match before its suggestions reach the queue.
  5. P5
    Everything elseArticles, blogs and Q&As, gap-filling for thin passages, caching, and other languages.
  6. +
    Option: topicsThe same flow for adding and checking topics on resources. See the Topics option page.
Open questions

To decide before building

  1. Who are the editors, and roughly how many hours a week can they give to Review?
  2. How many resources have no transcript? Those need transcription from audio first.
  3. Once accuracy is proven, may some suggestions skip review, for example sermons whose Scripture field names one passage?
  4. Should the site's “Resources on this verse” block live on gty.org, in the Bible app, or both?
