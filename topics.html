Topics, the same way

The same plugin could manage topics too. Agents read each resource and suggest topics from the existing list, or propose a new one. Editors decide, and they own the topic list. Approved topics are written to the Topics field resources already have, so the site keeps working as it does today.

What's different from passages

Topics are a list that grows, and most content already has some

Bible passages are fixed. Topics aren't: the list can gain new topics, two topics can turn out to mean the same thing, and a topic can get too broad to be useful. Most resources also already have topics from the old site. So the agents do three jobs here.

+

Fill gaps

Suggest topics from the existing list for resources that have none, or too few.

Check what's there

Flag an existing topic that seems a weak fit. Agents never remove one. An editor keeps it or removes it.

Propose new topics

When many resources share a subject the list doesn't cover, propose one new topic with the closest existing topics beside it.

Only editors create, rename or merge topics

Topic links use the same three strengths, with names that fit topics: ●●● Main topic, ●●○ Covered, ●○○ Touches on. Only Main topic and Covered are written to the resource's Topics field and shown on the site.

Workflow

Same five steps, plus the topic list

1

Import

Existing topic links come in as approved, from the old site. An agent later suggests a strength for each.

Script
2

Read

An agent reads the resource and its passages, then suggests topics from the list with a strength and a quote. It also flags weak existing topics.

Agent
3

Check

Code confirms the quotes and that each topic exists. Proposals for new topics from different runs are grouped, so the same idea shows up once.

Code + second agent
4

Decide

Editors approve topics on resources, and separately decide on new topics: create one, use an existing topic instead, or reject it.

Editor
5

Publish

Approved Main and Covered topics are written to the resource's Topics field. Topic pages and the API rank resources by strength.

Strapi + API
  • Editors own the topic list.Agents can propose a topic. Only an editor creates, renames, moves or merges one.
  • Existing topics are safe.An agent can flag a topic as a weak fit but can't remove it. The old site's links stay until an editor decides.
  • Existing topics come first.Agents must pick from the current list. A new topic is proposed only when nothing close exists, and the closest matches are always shown.
  • Merges keep links working.Merging “Worry” into “Anxiety and Worry” moves every resource across and keeps the old slug as a redirect.

Under the hood

A second links table, written back to Topics

Topic links get their own collection, topic-link, shaped like scripture-link: resource, topic, strength, status, source, evidence, pinned rank, and who decided. The plugin's table records why a topic was chosen. Approved Main topic and Covered links are copied into each resource's Topics relation, so pages and apps that already read Topics need no changes.

A small topic-proposal collection holds suggested new topics: the name, a suggested parent group, the resources behind it, the closest existing topics, and the editor's decision.

Plan

Where this fits

Topics can start once the Review screen exists, after Scripture Map phase 3. Passages help agents choose topics, so doing passages first makes topic suggestions better.

  1. T1
    Import and topic listImport existing topic links as approved. Add the Topics tab with health checks, and topic editing with other names.
  2. T2
    Fill gapsAgents suggest topics for resources with none or one. Topics section in Review and in the Content Manager panel.
  3. T3
    Check existing and propose newWeak-fit flags, new topic proposals, and merges with redirects.
  4. T4
    Devotionals and clipsThese have no Topics field today. Adding one is a schema change to decide on separately.
Open questions

To decide before building

  1. Who owns the topic list? One person, or any editor with a second editor confirming a merge?
  2. Is there a target number of topics per resource, for example 2 to 5?
  3. Should topic pages on the site show strength, or use it only for ordering?
  4. Do products and conferences go through the same review, or stay managed by hand?
